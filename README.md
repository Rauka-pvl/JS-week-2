# DataShare API — Неделя 2

REST-сервер на Node.js и Express.js. Вторая практическая работа в 8-недельном
проекте **DataShare**: бизнес-логика из недели 1 превращается в HTTP-сервис.

- **Студент:** Аделканов Рауат
- **Группа:** CS-302(с)
- **Вариант:** 2 — Книги
- **Индивидуальное усложнение:** H — `GET /api/items/stats` (дополнительно реализованы
  сортировка, `minPrice`/`maxPrice` и пагинация)
- **Дисциплина:** Веб-программирование на JavaScript

## Описание

API выполняет CRUD-операции над книгами, принимает параметры пути, query-параметры
и JSON body, возвращает корректные HTTP-статусы и JSON-ошибки. Каждый запрос
логируется собственным middleware. Данные хранятся в массиве в памяти —
после перезапуска сервера изменения сбрасываются (MongoDB появится на неделе 3).

## Требования

- Node.js **v18+** (разработано и проверено на **v24.6.0**)
- Express **5.x**
- Postman — для проверки API

## Установка и запуск

```bash
npm install
npm start
```

Сервер стартует на `http://localhost:3000` (порт можно изменить переменной `PORT`).
Для разработки с автоперезапуском: `npm run dev`.

## Endpoints

| Метод  | URL                   | Назначение                           | Статусы         |
| ------ | --------------------- | ------------------------------------ | --------------- |
| GET    | `/`                   | Проверка работы API                  | 200             |
| GET    | `/api/items`          | Все книги (+ фильтры, сортировка)    | 200 / 400       |
| GET    | `/api/items/stats`    | Статистика (вариант H)               | 200             |
| GET    | `/api/items/:id`      | Одна книга                           | 200 / 400 / 404 |
| POST   | `/api/items`          | Создать книгу                        | 201 / 400       |
| PUT    | `/api/items/:id`      | Изменить книгу (частично)            | 200 / 400 / 404 |
| DELETE | `/api/items/:id`      | Удалить книгу                        | 200 / 400 / 404 |
| \*     | любой другой          | Неизвестный маршрут                  | 404             |

### Query-параметры `GET /api/items`

| Параметр             | Пример                  | Описание                                              |
| -------------------- | ----------------------- | ----------------------------------------------------- |
| `search`             | `?search=дьявол`        | Поиск по `title` и `description` без учёта регистра   |
| `category`           | `?category=Фантастика`  | Фильтр по категории без учёта регистра                |
| `minPrice`/`maxPrice`| `?minPrice=3000`        | Диапазон цен                                          |
| `sort` + `order`     | `?sort=price&order=desc`| Сортировка по `price`, `createdAt`, `title`, `year`   |
| `page` + `limit`     | `?page=2&limit=3`       | Пагинация (в ответ добавляется объект `pagination`)   |

Параметры можно комбинировать: `?category=Роман&sort=price&order=desc`.

### Примеры запросов и ответов

**`GET /api/items`** — поле `count` вычисляется, а не задаётся вручную:

```json
{ "success": true, "count": 10, "data": [ ... ] }
```

**`POST /api/items`** — обязательные поля `title`, `description`, `category`, `price`;
необязательные `author`, `year`. Сервер сам добавляет `id` и `createdAt`:

```json
{
  "title": "Понедельник начинается в субботу",
  "description": "Сатирическая повесть о программисте Привалове и НИИЧАВО",
  "category": "Фантастика",
  "price": 3100,
  "author": "Аркадий и Борис Стругацкие",
  "year": 1965
}
```

**Ошибка валидации (400):**

```json
{
  "success": false,
  "error": "Некорректные данные",
  "details": ["Поле \"price\" должно быть неотрицательным числом"]
}
```

**`PUT /api/items/:id`** — можно передать только изменяемые поля, например `{ "price": 3999 }`.
Поля `id` и `createdAt` изменить нельзя — они игнорируются. Добавляется `updatedAt`.

**`GET /api/items/stats`:**

```json
{
  "success": true,
  "data": {
    "count": 10,
    "totalPrice": 38000,
    "minPrice": 2500,
    "maxPrice": 5900,
    "averagePrice": 3800,
    "categories": ["Роман", "Фантастика", "Магический реализм", "Детектив", "Фэнтези", "Наука"],
    "byCategory": { "Роман": { "count": 3, "totalPrice": 10500 }, "...": "..." }
  }
}
```

## Обработка ошибок

| Ситуация                                 | Статус |
| ---------------------------------------- | ------ |
| Неизвестный endpoint                     | 404    |
| Несуществующий id                        | 404    |
| Некорректный id (`/api/items/abc`)       | 400    |
| Неполный POST                            | 400    |
| Некорректный `price` (строка, < 0)       | 400    |
| Некорректный JSON в теле                 | 400    |
| Пустой PUT без изменяемых полей          | 400    |
| Непредвиденная ошибка сервера            | 500    |

Все ошибки возвращаются в формате JSON, сервер при этом продолжает работать.

## Middleware

- `express.json()` — разбирает JSON-тело запроса в `req.body`.
- `logger` (`src/middleware/logger.js`) — собственное middleware: выводит время, метод
  и URL каждого запроса, а после ответа — статус и время обработки, затем вызывает `next()`:

  ```
  [2026-10-05T12:53:22.719Z] DELETE /api/items/2
    -> 200 (0 ms)
  ```

- `notFound` — отвечает 404 JSON на неизвестные маршруты.
- `errorHandler` — централизованный обработчик ошибок (4 аргумента).

## Postman

## Контрольные вопросы и ответы

**1. Что такое REST API?**

REST (Representational State Transfer) — архитектурный стиль построения API поверх HTTP.
Данные представлены как **ресурсы** с уникальными URL (`/api/items`, `/api/items/3`),
а действия над ними выражаются HTTP-методами: `GET` — получить, `POST` — создать,
`PUT`/`PATCH` — изменить, `DELETE` — удалить. Сервер не хранит состояние клиента между
запросами (stateless), обмен обычно идёт в формате JSON, а результат сообщается
HTTP-статусом.

**2. Что такое HTTP request/response?**

HTTP работает по схеме «запрос — ответ». **Request** (запрос) отправляет клиент:
он содержит метод (`GET`, `POST`…), URL, заголовки (например, `Content-Type`)
и необязательное тело. **Response** (ответ) возвращает сервер: статус-код
(`200`, `201`, `404`…), заголовки и тело (у нас — JSON). В Express они представлены
объектами `req` и `res`.

**3. Зачем Express?**

Встроенный модуль `http` в Node.js очень низкоуровневый: маршруты, разбор URL,
тела и параметров пришлось бы писать вручную. Express — минималистичный фреймворк,
который даёт удобную маршрутизацию (`app.get`, `Router`), систему middleware,
готовый разбор JSON, параметров и query, а также удобные методы ответа
(`res.status()`, `res.json()`).

**4. Что делает express.json()?**

Это встроенное middleware, которое читает тело запроса с заголовком
`Content-Type: application/json`, разбирает (парсит) JSON и кладёт получившийся
объект в `req.body`. Без него `req.body` будет `undefined`. Если JSON некорректный,
middleware передаёт ошибку дальше — в проекте её ловит `errorHandler` и отвечает 400.

**5. Чем req.params отличается от req.query?**

`req.params` — параметры **пути**, объявленные в маршруте через двоеточие:
для маршрута `/api/items/:id` и запроса `/api/items/3` будет `req.params.id === "3"`.
Обычно идентифицируют конкретный ресурс. `req.query` — параметры **строки запроса**
после `?`: для `/api/items?search=mac&category=Роман` будет
`{ search: "mac", category: "Роман" }`. Используются для фильтрации, поиска,
сортировки и пагинации. Оба значения всегда приходят строками — поэтому id
преобразуется в число через `parseId`.

**6. Как получить req.body?**

Подключить `app.use(express.json())` **до** маршрутов, а клиент должен отправить
тело с заголовком `Content-Type: application/json`. После этого в обработчике
данные доступны как `req.body`, например `const { title, price } = req.body;`.

**7. Что делает res.json()?**

Преобразует JavaScript-объект в JSON-строку, устанавливает заголовок
`Content-Type: application/json` и отправляет ответ клиенту, завершая запрос.
Обычно вызывается вместе со статусом: `res.status(201).json({ success: true, data })`.

**8. Почему POST обычно возвращает 201?**

Статус `201 Created` означает, что запрос выполнен **и в результате создан новый
ресурс**. Это точнее, чем общий `200 OK`: клиент сразу понимает, что запись создана.
В теле ответа принято возвращать созданный объект (с присвоенным `id` и `createdAt`).

**9. Когда возвращается 404?**

`404 Not Found` — когда запрошенный ресурс не существует. В проекте: книга с таким
`id` не найдена (в GET, PUT, DELETE), книга уже удалена, или запрошен неизвестный
маршрут (`/api/unknown`). Ошибки в самих данных запроса (неполный body, неверная
цена) — это не 404, а `400 Bad Request`.

**10. Что такое middleware и next()?**

Middleware — функция вида `(req, res, next) => { ... }`, которая выполняется в цепочке
между получением запроса и отправкой ответа. Она может прочитать или изменить
`req`/`res`, завершить запрос ответом или передать управление дальше, вызвав `next()`.
Если не вызвать ни `next()`, ни отправку ответа — запрос «зависнет». `next(err)`
передаёт ошибку в обработчик ошибок. Примеры в проекте: `express.json()`, `logger`,
`notFound`, `errorHandler`.

**11. Зачем разделять routes и controllers?**

Это разделение ответственности. **Routes** описывают, *какой* URL и метод
обрабатываются (карта API), а **controllers** — *как* обрабатывается запрос
(логика, валидация, ответ). Так код легче читать, тестировать и поддерживать:
можно изменить логику, не трогая маршруты, переиспользовать контроллеры,
а при росте проекта добавлять новые ресурсы по тому же шаблону.

**12. Почему данные исчезают после перезапуска?**

Данные хранятся в обычном массиве JavaScript в **оперативной памяти** процесса Node.js.
При остановке сервера процесс завершается и память освобождается. При новом
запуске модуль `items.js` загружается заново с исходными 10 книгами — все созданные,
изменённые и удалённые записи теряются. Для постоянного хранения нужна база данных.

**13. Что изменится при подключении MongoDB?**

Данные будут храниться в базе на диске и сохраняться между перезапусками.
Массив `items` заменится коллекцией MongoDB, а операции над массивом — запросами к БД
(`find`, `insertOne`, `updateOne`, `deleteOne`). Эти запросы асинхронные, поэтому
контроллеры станут `async` и будут использовать `await` с обработкой ошибок
через `try/catch`. `id` будет генерироваться базой (`_id` типа ObjectId), а фильтры,
сортировку и пагинацию можно будет выполнять силами самой БД. Структура
routes/controllers при этом сохранится.
